Gateway 路由、鉴权与过滤器

Lesson 0003 · 预计阅读 8 分钟

Gateway 做了什么？一个请求的旅程

想象浏览器发了 POST /api/v1/orders。这个请求不会直接到达 sc-purchase-service，它首先进入 Gateway（端口 8080）—— 然后才有后面的一切。Gateway 是微服务体系的统一入口，在这扇门前完成三件事：路由、鉴权、透传。

浏览器 → Gateway (8080) ├─ 1. 路由匹配: /api/v1/orders/** → sc-purchase-service ├─ 2. JWT 鉴权: Bearer token 有效？ └─ 3. 透传头: X-User-Id, X-User-Role → 下游服务

路由：Predicate + URI

打开 gateway 的 application.yml，核心结构非常清晰：

cloud:
  gateway:
    routes:
      - id: sc-purchase-service              # 路由唯一标识
        uri: lb://sc-purchase-service         # 转发目标
        predicates:
          - Path=/api/v1/orders/**         # 匹配条件

每条路由是 predicate（匹配条件）+ uri（目标地址） 的组合。Predicate 决定了"这个请求归谁管"，URI 决定了"往哪发"。

Gateway 启动后，所有 5 条路由都会被加载成一个匹配表。收到请求时，从上到下依次匹配 predicates，命中后就不再继续：

路由 id匹配路径转发到
sc-auth-service/api/v1/auth/**lb://sc-auth-service
sc-supplier-service/api/v1/suppliers/**lb://sc-supplier-service
sc-purchase-service/api/v1/orders/**lb://sc-purchase-service
sc-inventory-service/api/v1/inventory/**lb://sc-inventory-service
sc-payment-service/api/v1/payments/**lb://sc-payment-service

注意 server.webflux.discovery.locator.enabled: false —— 这行配置禁用了 Gateway 的"自动发现路由"功能。如果设为 true，Gateway 会根据 Nacos 里注册的服务名自动生成 /服务名/** 的路由，不需要手动写上面这堆。但项目中关闭了它：手动声明路由更可控，不暴露你不打算开放的服务。

鉴权：GlobalFilter 如何拦截每一个请求

路由只解决了"往哪发"，但没有解决"谁可以发"。这个项目里，鉴权由 JwtAuthFilter 完成。

它实现了两个关键接口：

接口作用
GlobalFilter全局过滤器 — 对所有经过 Gateway 的请求生效
Ordered决定过滤器执行顺序 — 数字越小越先执行

getOrder() 返回 -100，这是一个很靠前的值（Spring Cloud Gateway 内置过滤器默认是 0），确保鉴权在其他业务逻辑之前完成。

GlobalFilter vs GatewayFilter：GlobalFilter 作用于所有路由，GatewayFilter 作用于特定路由（写在路由配置的 filters 字段里）。JwtAuthFilter 用的是 GlobalFilter，因为鉴权不应该按路由粒度开关——要么全做，要么出安全漏洞。

逐行拆解 JwtAuthFilter

// 1. 白名单 — 这两个路径不需要 token
private static final List<String> PUBLIC_PATHS = List.of(
        "/api/v1/auth/register",
        "/api/v1/auth/login"
);

// 2. 匹配白名单则直接放行
if (PUBLIC_PATHS.contains(path)) {
    return chain.filter(exchange);    // 不校验，直接交给下游
}

// 3. 提取 Authorization 头
String authHeader = exchange.getRequest()
        .getHeaders().getFirst(HttpHeaders.AUTHORIZATION);
if (authHeader == null || !authHeader.startsWith("Bearer ")) {
    exchange.getResponse().setStatusCode(HttpStatus.UNAUTHORIZED); // 401
    return exchange.getResponse().setComplete();
}

// 4. 解析 JWT，提取 claims
String token = authHeader.substring(7);   // 去掉 "Bearer "
Claims claims = Jwts.parser()
        .verifyWith(key)
        .build()
        .parseSignedClaims(token)
        .getPayload();

// 5. 把用户信息注入请求头，透传给下游
exchange.getRequest().mutate()
        .header("X-User-Id", claims.getSubject())       // JWT sub = userId
        .header("X-User-Role", claims.get("role", String.class));

最后一步是关键设计：Gateway 自己不查数据库、不维护会话，它只做校验和透传。验证通过后，把 X-User-Id 和 X-User-Role 两个自定义头注入请求，后续的 sc-purchase-service、sc-inventory-service 直接从请求头里拿，不需要再解析 JWT。

为什么这样设计？ 每个下游服务不需要依赖 jjwt 库、不需要知道 JWT 密钥。关注点分离：Gateway 管认证（是谁），下游服务管授权（能干什么）。这也避免了每个服务反复解析同一枚 token 的性能浪费。

JWT 从哪来：sc-auth-service 的签发侧

现在看链条的另一端。用户登录时，AuthController 调 AuthService 验证密码，然后 JwtUtil 生成 token：

public String generateToken(Long userId, String role) {
    return Jwts.builder()
            .subject(userId.toString())      // → Gateway 取出来放 X-User-Id
            .claim("role", role)             // → Gateway 取出来放 X-User-Role
            .issuedAt(new Date())
            .expiration(new Date(now + 3600000)) // 1 小时过期
            .signWith(key)
            .compact();
}

注意 Gateway 的 JwtAuthFilter 和 sc-auth-service 的 JwtUtil 用的 key 必须一致——两边都从 jwt.secret 配置项读取。如果对不上，Gateway 验证签名时直接抛异常，所有带 token 的请求都 401。

完整链路一览

1. POST /api/v1/auth/login { username, password } 2. sc-auth-service 验证密码 → JwtUtil.generateToken → 返回 JWT 3. 浏览器存下 token，后续请求带 Authorization: Bearer <token> 4. GET /api/v1/orders → Gateway (8080) 5. JwtAuthFilter: PUBLIC_PATHS 不匹配 → 解析 token → 成功 6. 注入 X-User-Id: 1, X-User-Role: ADMIN 7. 路由匹配: /api/v1/orders/** → lb://sc-purchase-service 8. 请求转发到 sc-purchase-service，带着透传头
安全提醒：当前 jwt.secret 用的是占位字符串 change-me-to-a-long-random-string-at-least-256-bits，生产环境必须替换为随机密钥并妥善保管。另外，X-User-Id 和 X-User-Role 是从客户端 token 里解出来的，如果下游服务信任这些头来做权限判断，务必确保只有 Gateway 能访问下游服务（通过网络隔离），否则攻击者可以绕过 Gateway 直接伪造这些头。
