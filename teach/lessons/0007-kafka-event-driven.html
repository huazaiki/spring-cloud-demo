你不需要等我：Kafka 与事件驱动

Lesson 0007 · 预计阅读 9 分钟

回顾：两种调用模式的根本差异

前面的课已经反复提到了同步调用（Feign）和异步消息（Kafka）的划分。这一课不再重复"什么时候用哪个"——而是深入理解：异步消息改变的不仅是性能，更是服务之间的关系模型。

同步调用 (Feign)异步消息 (Kafka)
关系模型调用方 — 被调方生产者 — 消费者
耦合方式调用方知道被调方的服务名和 API双方只知道同一个 Topic 名
失败传播调用方立即感知，需要熔断保护消费者自行处理重试，生产者不感知
时间耦合双方必须同时在线任何一方随时上下线

同步调用的关系像电话：你拨号，对方必须接，你等对方说完才能继续。异步消息的关系像邮件：你发送，对方什么时候看、什么时候回，你不需要知道——甚至对方换了一个人看这封邮件，你也不关心。

Topic：契约的新形态

在 Feign 的模型里，purchase-service 和 inventory-service 之间的契约是 @FeignClient 接口——一份"我提供这些方法，你按这个签名调"的说明书。在 Kafka 的模型里，契约变成了一条 Topic：一个命名的消息通道，生产者往里写，消费者从里读。 

# purchase-service application.yml (已有配置)
spring:
  kafka:
    bootstrap-servers: localhost:9092
    producer:
      key-serializer: StringSerializer
      value-serializer: JsonSerializer          # ← 消息体自动序列化为 JSON

生产者不需要知道消费者是谁。它只做一件事：把事件序列化成 JSON，发到一个 Topic。比如入库完成后：

inventory-service (Producer) │ ├─ 1. 数据库: UPDATE inventory SET quantity = quantity + 100 │ └─ 2. 发消息到 Topic "inventory.received" { orderId: 42, itemId: 3, quantity: 100, receivedAt: "..." } ↓ Kafka Broker 持久化消息 payment-service (Consumer) │ └─ 3. 从 Topic "inventory.received" 读到消息 → 执行: INSERT INTO payable (order_id, ...)

关键设计：如果 payment-service 当时挂了（还没部署、正在重启、数据库满了），消息不会丢失——Kafka 把它持久化在磁盘上。payment-service 恢复后，从上次中断的地方继续消费。这就是异步消息的核心优势：时间解耦。

从"命令"到"事件"：思维模型的转变

同步调用是命令式的：inventoryClient.reserveStock() 明确地告诉 inventory-service"你去执行这个操作"。异步消息是事件驱动的：生产者只是宣告"这件事已经发生了"，不指定谁来处理。

命令 (Command)事件 (Event)
"给我预留库存""库存已经入库了"
指定执行者不指定消费者
调用方知道 API只约定消息格式
失败 = 调用方感知失败 = 消费者自己处理
Feign / gRPCKafka / RabbitMQ
事件驱动的真正价值：如果三个月后需要加一个新功能——"库存入库后自动发邮件通知采购员"，你不改 inventory-service 一行代码。加一个新的 Consumer 订阅同一个 Topic 就行。生产者和原有消费者完全不受影响。这叫"开放扩展，封闭修改"——不是 OOP 里的继承多态，而是架构级别的扩展点。

消息不会丢……但可能被处理多次

Kafka 默认提供 at-least-once（至少一次）语义：每条消息保证被消费，但不保证只被消费一次。原因在于：消费者处理完消息后向 Kafka 提交 offset（进度），如果处理成功但提交 offset 失败（网络抖动），恢复后会重新消费同一条消息。

消费者读到消息 offset=42: ① 执行业务逻辑: INSERT INTO payable ... ← 成功！ ② 提交 offset=43 给 Kafka ← 网络超时，提交失败 ③ 消费者重启 ④ 重新读到 offset=42 ← 同一条消息又来了一遍 ⑤ 再次 INSERT INTO payable ... ← 重复插入！

解决办法不是让 Kafka"保证不重复"——这是 CAP 定理下做不到的。而是让消费者变得幂等：同一条消息处理两次，结果和一次一样。常用的手段：给每条消息带一个唯一 ID（如 order_no），消费前先检查"这个 ID 我已经处理过了吗"。

幂等性不是可选的：在分布式系统中，任何消息驱动的消费者都应该设计为幂等的。因为你永远无法 100% 保证一条消息只被投递一次——你可以无限接近 exactly-once，但做不到绝对的 exactly-once。

Kafka 在整个体系中的位置

把 Kafka 放回项目的整体架构里看，它的角色变得清晰：

组件通信模式耦合度典型场景
Gateway外部 HTTP → 内部路由无（纯转发）统一入口
Feign同步 RPC调用方依赖被调方名和 API审批 → 预留库存
Kafka异步消息只依赖 Topic 名和消息格式入库 → 生成应付账款

三者不是互相替代，而是各自解决不同的问题。一个成熟微服务系统的通信层，通常三者都有——Gateway 管入口、Feign 管同步业务链、Kafka 管异步通知链。
