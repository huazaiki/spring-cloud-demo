跨服务的回滚：Seata 分布式事务

Lesson 0006 · 预计阅读 9 分钟

单体事务在微服务时代碎掉了

一个采购单审批，在单体应用里就是一个 @Transactional 方法：

@Transactional approveOrder(orderId): ① UPDATE purchase_order SET status = 'APPROVED' ② UPDATE inventory SET reserved = reserved + quantity // 失败！ → ① 自动回滚，所有改动取消

但在微服务里，① 在 sc-purchase-service 的数据库（purchase_db），② 通过 Feign 调 sc-inventory-service 操作另一个数据库（inventory_db）。两个 @Transactional 互不感知。② 失败了，① 已经提交了——数据不一致。

分布式事务的困境：每个服务有自己的数据库，@Transactional 只控制本地的数据库连接。跨服务的操作天然没有"回滚"概念——你不可能 undo 另一个服务已经 commit 的事务。

Seata AT 模式的核心思想：给数据库加"撤回键"

Seata 的 AT（Automatic Transaction）模式解决这个问题的方式出奇简洁：在每条 UPDATE 之前拍一张快照（before image），之后拍一张快照（after image），存进一张叫 undo_log 的表里。需要回滚时，拿 before image 覆盖回数据库。

执 行： ① SELECT * FROM inventory WHERE item_id = 1 → before image: { id: 1, item_id: 1, quantity: 100 } ② UPDATE inventory SET quantity = 80 WHERE item_id = 1 ③ SELECT * FROM inventory WHERE item_id = 1 → after image: { id: 1, item_id: 1, quantity: 80 } ④ INSERT INTO undo_log (before_image, after_image, branch_id) 回 滚： ⑤ SELECT before_image FROM undo_log WHERE branch_id = ? ⑥ UPDATE inventory SET quantity = 100 WHERE item_id = 1 → 数据恢复到更新前的状态

关键洞察：不需要你写任何回滚代码。Seata 通过记录 UNDO SQL 自动生成反向操作。INSERT 变成 DELETE，UPDATE 变回原来的值，DELETE 变成 INSERT——所有基于单行操作的 SQL 都能自动回滚。

"AT" 为什么叫 Automatic Transaction？ 因为对开发者来说，你只需要在入口方法上加 @GlobalTransactional，其余完全不用管——Seata 自动拦截所有 SQL、自动记录 undo_log、自动回滚。不需要写补偿代码，不需要手动维护逆向操作。

三角色架构：TC、TM、RM

Seata 把分布式事务拆成了三个独立角色：

角色谁担任职责
TC (Transaction Coordinator)Seata Server（独立进程）维护全局事务状态，协调提交或回滚
TM (Transaction Manager)标注了 @GlobalTransactional 的服务声明事务边界，发起提交或回滚
RM (Resource Manager)每个参与事务的服务的数据库管理本地事务，上报分支状态，执行 undo_log

sc-purchase-service 的 approveOrder 方法加 @GlobalTransactional 后，它变成 TM。sc-purchase-service 和 sc-inventory-service 各自的数据库操作充当 RM。TC 是独立的 Seata Server，三者通过 netty 通信。

sc-purchase-service (TM) │ ├─→ 自己的 DB (RM) → undo_log 记录 purchase 的改动 │ └─→ Feign → sc-inventory-service → 它的 DB (RM) → undo_log 记录 inventory 的改动 Seata Server (TC) 协调以上所有 RM 的提交/回滚

不是完整的二阶段提交

传统 2PC（Two-Phase Commit）的流程是：Phase 1 所有参与者锁定资源但不提交 → Phase 2 协调者统一发 Commit 或 Rollback。这有一个严重问题：Phase 1 的资源锁定期间，其他事务无法访问，吞吐量极低。

Seata AT 做了关键优化：Phase 1 直接提交本地事务——锁只持有极短时间，其他事务立即可以看到修改后的数据。如果后续需要回滚，靠 undo_log 把数据恢复。这意味着：

隔离级别的代价：AT 模式下，在全局事务未完成（未全局提交或回滚）的时间窗口内，其他事务可能读到了"中间状态"的数据。如果你的业务对隔离级别要求极高（如金融转账），需要评估这个窗口期的风险。大多数业务场景（如采购审批）可以接受。

什么时候该用 AT，什么时候不该

这个判断跟上一课的 Feign vs Kafka 形成了呼应：

场景AT 模式最终一致性 + 补偿
创建采购单 + 预留库存合适。 两步必须同时成功或同时回滚，强一致性不合适。补偿逻辑复杂且延迟不可控
入库完成 → 生成应付账款重了。 异步+宽松延迟的场景，AT 引入额外复杂度合适。 Kafka 消息 + 消费者重试就够
跨 3 个以上服务的复杂流程需要评估。参与方越多，全局事务锁持有时间越长考虑 Saga 模式（编排/编排）更合适

选择的核心标准：你是否需要"要么全成功要么全失败"的语义。需要 → AT，不需要或可以接受短暂不一致 → 消息 + 补偿。这和第四课同步异步的判断是同一根决策树上的两个分支。

更深一层：为什么数据库事务不能跨网络

分布式事务之所以难，根本原因是 CAP 定理中的 Partition Tolerance 与 Consistency 的冲突。当你把两个数据库放在不同的网络节点上，网络分区随时可能发生——TC 联系不到 RM 了，怎么办？一直等？超时回滚？超时提交？

All distributed transaction solutions are, at heart, strategies for handling uncertainty during network partitions. Seata AT 的策略是：Phase 1 先提交（乐观），Phase 2 如果需要回滚，用 undo_log 补救。这不是完美的一致性——两个 Phase 之间存在不一致窗口——但它在大部分业务场景中足够好。
