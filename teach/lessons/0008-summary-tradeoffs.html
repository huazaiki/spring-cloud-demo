每一层复杂度，对应一个被解决的问题

Lesson 0008 · 预计阅读 7 分钟

先看全景：你现在知道的

一个请求从浏览器到数据库，穿过了这些层：

浏览器 │ ├─ Gateway ──── 统一入口、路由匹配、JWT 鉴权 │ ├─ Nacos ────── 服务注册与发现，地址从 IP 变成服务名 │ ├─ Feign ────── 声明式调用，Remote 伪装成 Local │ ├─ Resilience4j 熔断、重试、降级，下游挂了不拖死上游 │ ├─ Seata ────── 跨服务事务回滚，undo_log 自动补偿 │ └─ Kafka ────── 异步解耦，事件驱动，削峰填谷

每一层的存在，都是因为单体应用里不需要考虑的问题，在微服务架构里变成了必须面对的挑战。

七节课的代价-收益表

组件解决的分布式问题引入的复杂度
Gateway没有统一入口，每个服务暴露端口，鉴权重复多一跳网络延迟；需要维护路由配置
NacosIP 硬编码导致扩容/缩容需要手动改配置引入注册中心单点（需要集群部署）
Feign手写 HTTP 调用代码，URL 拼接易错、不可维护动态代理增加调用链深度，调试变复杂
Resilience4j下游不可用时线程堆积导致级联故障需要为每个依赖配置熔断参数，Fallback 增加代码量
Seata跨数据库的操作无法自动回滚undo_log 增加存储开销；TC 单点风险；隔离窗口
Kafka服务间同步耦合，一损俱损消息顺序、幂等、重复消费、延迟——全变成你的责任

没有免费的午餐。微服务不会让你的系统变简单——它把单体内部的方法调用，变成了网络上的分布式协调问题。你获得的是独立部署、独立扩缩容、技术栈异构的能力，付出的代价是网络延迟、分布式事务、熔断降级、消息一致性。

三个反复出现的设计主题

七节课下来，有三个概念反复出现，不是巧合——它们是分布式系统的核心张力：

1. 解耦

Nacos 解耦了服务名和 IP。Feign 解耦了业务意图和 HTTP 实现。Kafka 解耦了生产者和消费者。Gateway 解耦了认证和业务逻辑。每一步解耦都增加了一层抽象，而每一层抽象都换来一个维度的灵活性。

解耦的方向是一致的：让修改一个东西时，不需要同时修改依赖它的所有东西。但代价也一致：出问题时排查链路变长。

2. 防御

单体里不需要防御——方法调用不会失败。微服务里每一次远程调用都可能失败。Resilience4j 的断路器、Seata 的 undo_log、Kafka 的持久化——本质都是在"一定会出问题"的假设下设计系统。这不是悲观，是诚实。

3. 声明优于指令

Feign 的 `@FeignClient`、Gateway 的 YAML 路由、Seata 的 `@GlobalTransactional`——模式一致：你声明意图，框架负责实现。这不是巧合，而是分布式系统复杂度过高的必然结果。你的工作记忆装不下 URL 拼接 + 负载均衡 + 熔断 + 重试 + 序列化，所以把它们下沉到框架，把意图上浮到注解。

什么时候微服务不值得？

自检问题：你的团队是否配备了 Nacos 集群运维、Kafka Topic 管理、Seata TC 部署、链路追踪排查的能力？如果没有，微服务带来的运维复杂度可能超过它解决的业务问题。

当以下条件同时满足时，单体可能是更好的选择：

  • 团队成员少于 5 人，一个人负责多个服务
  • 业务逻辑强耦合，拆开后事务边界模糊
  • 没有明确的独立扩缩容需求——所有模块流量同涨同跌
  • 没有多团队并行开发的需求

微服务解决的是组织规模的问题，不是代码质量的问题。如果你的组织规模还没到这个程度，先写一个好的单体——模块化、清晰的包结构、领域驱动——比提前拆成微服务明智得多。

回到你的 Mission

你在 MISSION.md 里写：

掌握 Spring Cloud 生态的核心组件和设计思想，能够独立设计、搭建和运维一个生产级微服务系统。

七节课下来，你应该能够：

  • 解释清楚一个请求从 Gateway 到数据库经过的每一层，以及每一层为什么存在
  • 在面对一个新的服务拆分问题时，有判断力地说出"这里该用 Feign 还是 Kafka，需要熔断吗，事务边界在哪"
  • 理解微服务的核心不是技术选型（Spring Cloud / K8s / Service Mesh），而是设计决策的权衡意识

最后一个是最重要的。技术会变——Spring Cloud 会升级，Kafka 可能被 Pulsar 替代，Seata 可能被 Saga 编排取代。但"解耦-防御-声明"的设计直觉、CAP 定理下的取舍意识、以及"复杂度必须换回价值"的工程务实——这些不会变。
